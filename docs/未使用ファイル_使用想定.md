3. ApiEndpoints.ts

これは結構使えます。

今は、

fetch("/api/assets")
fetch("/api/assets/bulk")
fetch(`/api/assets/${id}`)

とURLを直接書いています。

例えば、

export const ApiEndpoints = {
    assets: "/api/assets",
    assetsBulk: "/api/assets/bulk",
};

としておけば、

fetch(ApiEndpoints.assets)

とできます。

特にAPIが増えると、

/api/assets
/api/assets/bulk
/api/auth/login
/api/users
/api/audit-logs

などが散らばるので管理しやすくなります。

→ 残す。実装するならAPI整理のタイミングで使う。

そして、今回かなり大事なこと

以前作ったファイルの中には、「最初に想定していた設計」と「現在の実装方針」が変わったことで不要になったものがあります。

特に、

palette.ts
shadows.ts
typography.ts
components.ts

はその典型です。

最初はThemeを分割する想定でしたが、現在は theme/index.ts にまとめる方針になっています。

なので、

「以前作ったから使わないといけない」

ではありません。

今の設計に必要かどうかで判断して大丈夫です。

逆に ApiEndpoints.ts、AppLoading.tsx、storage.ts、ErrorMessage あたりは、今後の認証・エラー処理・API拡張で使い道がかなり明確です。

今日はこの仕分けをしておけば、帰省中にスマホでも「これは残す・これは削除」と設計判断できます。実際の削除や共通化は帰ってきてからで十分です。
